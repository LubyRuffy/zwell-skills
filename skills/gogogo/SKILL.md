# Gogogo

## 执行边界

将用户的真实任务连续推进到约定的交付结果；具体业务、命令和环境以目标仓库的 `AGENTS.md`、代码、任务定义和项目 skill 为准。优先使用可用的领域 skill，但不要因加载另一个 skill 擅自扩大范围或引入额外 PR 流程。

默认采用单人开发流程：**最新主线 → 独立 worktree 开发分支 → 测试与 review → 提交并推送开发分支 → 同步本地 main、集成 → 再验证并推送 main → 部署或发布 → 验收**。除非用户或项目明确另有要求，不在主工作区直接开发，不要求 PR。项目要求 PR、受保护分支或发布分支时遵守该规则。

本文的“主线”默认是 `main`；先确认项目约定的真实主分支与对应远端，不得硬造 `main` 或假定远端一定是 `origin`。已有授权持续有效；完整闭环不扩大用户授权的目标环境、发布渠道或操作范围。单纯修改技能内容不授权创建 issue、推送或部署本技能仓库。

## 闭环流程

1. 读取项目规则、Git 状态、worktree 列表和真实入口，明确验收标准；已有 issue 引用就复用，否则为任务创建追踪 issue。
2. 按“最新主线与 worktree”完成同步和隔离，再开始编辑。
3. 在开发前检查构建、测试、发布与部署任务，明确各交付端、版本来源及缺失项，避免到发布阶段才发现没有入口。
4. 复现缺陷或确认新功能的目标行为，追踪真实调用链和根因；先观察目标测试失败，再做最小实现。
5. 执行严格测试门槛，同步受影响的功能、契约、使用文档和 CHANGELOG，完成提交前 review。
6. 在开发分支提交本次变更；推送前重新 fetch 远端主线，若它已前进，则安全地把最新主线纳入开发分支，解决冲突并重跑受影响验证与 review。
7. 推送开发分支到正确远端，首次推送时设置 upstream，核对远端分支指向本次已验证提交；若同名远端分支已属于其他工作，先调查或换名，不覆盖。项目要求 PR/CI 时按项目流程完成并等待门禁。推送分支不代表已合入或已发布。
8. **开发分支推送成功后**，安全同步本地 `main` 到远端最新，再把完整分支结果集成到本地 `main`；在最终主线候选上重跑必要验证并通过 review，推送 `main` 后核对远端提交。受保护主线按项目规定合入，并在本地同步合入后的主线。
9. 从完整主线通过实际发布/部署入口交付，验证版本、产物与远端结果。
10. 交付验收通过后关闭 issue，清理本任务已集成且干净的 worktree 和本地分支；存在未交付工作时保留现场并说明状态。

## 最新主线与 worktree

- **首次编辑前必须成功获取远端最新主线**：先执行针对正确远端的 `git fetch --prune` 或项目规定的等价流程，核对远端主线 SHA。网络失败或无法确认最新状态时，不以旧的远端跟踪引用冒充最新基线。
- 本地主线干净且可安全操作时，在其所在工作区执行 `git pull --ff-only` 或等价快进同步。主线有未提交改动、被其他任务使用或已分叉时，保留现场，直接以本次 fetch 得到的远端主线提交建立独立 worktree，无需先修改原工作区。
- **默认使用独立 worktree 和任务分支**，例如 `git worktree add -b codex/<task> <path> <刚获取的远端主线提交>`。命令中的路径、远端和分支必须替换成已确认的实际值，不能使用 detached HEAD 承担开发。
- 创建后检查所在路径、当前分支和基线 SHA；新分支 HEAD 应等于选定的最新主线 SHA。复用已有任务 worktree 时，先审查其中改动，再安全 merge/rebase 最新主线并验证其为当前分支祖先，不能直接在陈旧基线上继续写代码。
- 不覆盖、删除、stash 或代交其他主体的改动，不强制重置分叉主线，不重写他人或已共享的提交。无法安全更新已有分支时，先隔离可独立完成的工作，再说明实际阻塞。
- 推送开发分支前再次 fetch；若远端主线前进，先纳入分支并验证。首次推送后不 rebase 或改写已共享的分支提交；后续主线再前进时以安全 merge 纳入分支、重验并再次推送，随后才同步本地 `main`。推送被并发提交拒绝时重新获取、集成和验证，不 force push。持续变化导致无法稳定交付时保留成果并报告，不无限重试。
- 开发分支推送后，检查本地 `main` 的工作区及其与远端主线的关系；干净且可快进时同步远端，再安全合入完整分支。若主工作区有其他任务的未提交改动、分叉或受保护分支规则阻止集成，不覆盖现场；保留已推送的开发分支，报告本地 `main` 尚未同步/集成，不能假装闭环已完成。
- 更新主线会改变候选发布内容，之前对旧提交的测试不能作为新候选的放行证据。

## 根因与实现约束

- 修 bug 或质量问题前，说明失败现象、复现证据、错误数据或状态来源、失效层，以及为什么选定的修复位置能解决通用问题。
- 有用户指定参考或上游实现时，检查其真实机制，不能凭名称推测行为。
- 禁止按具体题面、实体名、query 文案、客户名或测试文件名写样本特化分支。领域规则应能表述为可复用模式。
- 疑似硬编码的改动必须有原始失败测试和至少一个反例/干扰样本，并说明对应的通用机制。临时止血应明确标记 workaround 和清理项，不能伪装成长期修复。
- 三次修复仍被新反例推翻时，停止叠补丁，重新审视抽象与架构。

## 严格测试门槛

测试通过、编译通过、真实入口可用是不同证据，不能相互替代。先从项目规则、CI 和任务定义确定必须执行的检查；所有必需检查通过后才可提交、集成发布和宣称完成。

- 新功能或缺陷修复采用红绿验证：先运行能表达目标行为的测试，确认失败由目标能力缺失导致；实现后通过原测试、关键边界和反例测试。重构用同一组行为断言验证前后不变量。
- 运行受影响模块测试、项目要求的完整测试、静态检查和构建；不得只挑通过的测试或以缓存、历史结果替代当前候选的证据。
- Go 变更验证单元测试和受影响构建目标，按项目要求执行 vet/lint；前端变更验证类型检查、测试和生产构建；同时涉及前后端时分别验证。
- API、CLI、存储和外部适配器变更执行契约或集成测试；并发、取消、共享状态变更执行竞态测试；性能修改提供基准或性能证据。
- UI 修改做真实路径走测，关键 Web 流程更新并运行 E2E；桌面端验证真实窗口，移动端验证受影响平台的构建和实际运行路径。不能用 Web 预览代替桌面或移动端验收。
- Wails 桌面端、移动端、生成代码及跨平台产物，验证本次交付所需的对应入口和目标平台。缺少设备、SDK、签名、测试数据或环境时，列出确切缺口；必需项未运行、被跳过、超时或失败均为未通过，不能发布或关闭 issue。
- review 修复、冲突解决、版本变更和主线集成后，重新执行受影响检查；在最终主线候选上执行项目发布门禁，保留提交 SHA、命令、结果和未完成项。

## 提交前 Review Gate

- `git add`、`git commit`、`git push` 前必须通过 review。优先使用可用的 review skill/工具，否则做显式自审并说明结论；不因没有 PR 而省略审查。
- 检查根因与修复位置是否一致，有无样本特化、只修症状或测试投机；失败与成功证据、边界测试、文档和公开契约是否闭合。
- 检查版本来源、发布任务的实际副作用、产物与提交对应关系，以及未处理的脏工作区。
- 暂存区只允许包含本次交付文件，排除密钥、本地数据、构建产物和无关修改。
- 阻断问题修复后重跑受影响验证并重新 review；最终报告说明审查方式及结论。

## 发布与部署任务检查

开发前检查 `Makefile` 及其 include、Wails 3 的 Taskfile/任务配置、脚本、CI workflow 和发布文档，追踪任务的实际调用链。不能只凭任务名称判断其已完成发布，也不要为探测任务而直接运行可能产生副作用的命令。

为本次涉及的每个交付端记录：真实命令、目标环境/渠道、产物、版本来源、测试门禁和远端成功证据。

| 交付类型 | 常见入口示例 | 必须确认的结果 |
| --- | --- | --- |
| 服务端 | `make deploy` 或实际 Wails/任务入口 | 部署到指定环境，健康检查、运行版本和关键业务路径通过 |
| PC/桌面软件 | `make release` 或实际 Wails 3 发布任务 | 所需平台安装包上传到目标 GitHub Release，tag、版本、提交和附件一致 |
| 移动端 | `make mobile-android-release`、项目定义的 iOS 任务等 | 目标平台发布包及必要签名有效，上传到约定 Release/渠道，版本和附件一致 |

- 这些名称只是示例：`build`、打包、签名完成或创建本地文件不等于发布到 GitHub Release；CI 入队也不等于成功。
- 发现仓库存在 PC 或移动端软件，却缺少对应发布到 Release 的可执行任务，或任务只有构建没有上传能力时，**明确提醒用户提供或指定对应 Wails 3 / Make 任务**，说明缺少哪个平台、产物或上传步骤。已有且有文档的等价脚本/CI 可以复用，不强制改名。
- 缺少发布入口时继续完成可独立执行的开发、测试和审查，阻断受影响的发布阶段；不要擅自生成发布基础设施、猜测凭据或把缺项视为完成。用户授权补建后再实现并验证。
- 多端项目检查所有实际存在的客户端发布入口，但只执行本次授权范围内的发布。其他端缺项需要提醒，不擅自扩大成全平台发版。服务端没有部署入口且本次要求部署时，同样报告缺口并阻断部署。

## 版本自动递增

- 查明唯一版本来源与传播链，如 `VERSION`、包元数据、Wails 构建配置、Git tag 或 CI 版本任务；多个位置应由同一来源派生，不能分别手改成互相冲突的值。
- **每次新的发布必须自动得到严格递增且未占用的版本**。优先使用项目现有版本递增任务，检查实际实现；没有自动机制时，明确缺口，在已授权的发布工作范围内补齐最小机制和测试，超出范围则请用户提供任务，不得静默沿用旧版本。
- 以项目版本规则和实际已发布版本/tag 为依据，按语义版本或项目格式比较，不能用字符串排序猜大小。补丁修复默认递增 patch；功能或破坏性变更遵循项目 SemVer 规则，无法确定时先澄清发布类型。
- Android `versionCode`、iOS build number 等构建号也必须按平台及项目规则递增，并与展示版本对应；同一发布的多平台产物使用一致的发布版本。
- 发布前查询远端 tag、Release 和适用渠道，核对新版本未被占用；并发发布占用候选版本时重新分配、构建和验证，禁止覆盖已有 tag、Release 附件或移动端构建号。
- 版本变更应纳入本次发布提交；若项目由 tag/CI 派生版本，需证明 tag、源码 SHA 与产物一致。不要让发布脚本临时修改源码后，把脏工作区产物当作已验证主线发布。
- 发布失败重试先确认远端状态和已执行步骤。同一发布的安全重试复用已分配版本，不因每次重试重复自增；若内容变化或版本已用于另一发布，应分配新版本并重新验证。部分上传状态不明确时先核实，不能覆盖或盲目重复发布。

## 主线发布门槛与收尾

- “完整主线”同时满足：包含最新获取的远端主线、本次所有待发布结果和版本变更；工作区、暂存区干净；最终候选提交已通过严格测试与 review；没有混入其他主体未完成或未验证的内容。
- 默认先推送已验证的开发分支，再从完整主线推送并发起部署/发布；每次执行前显式检查路径、分支、SHA 和干净状态。项目用 tag/CI 发布时，tag 必须指向该已验证主线提交，并等待关联任务完成。
- 主工作区被并发工作占用时，不强制切换或占用已 checkout 的主线，不以 detached worktree 或“release”临时分支绕过门槛；先保留已验证任务分支，等待能安全集成和发布的时机。
- 禁止通过 stash 隐藏改动或 cherry-pick 本次部分提交来抢发。通过 merge、rebase 或 squash merge 集成完整任务结果；用户明确要求其他搬运方式时，仍须验证最终完整主线。
- 集成后若存在其他主体待统一发布的内容，记录已集成到哪里，等待统一发布，不擅自接管其任务。
- 发布验收检查实际远端状态：服务端健康、版本及关键业务路径；软件 Release 的 tag、源码提交、目标平台附件及安装/启动验证。仅推送成功、脚本退出 0 或本地产物存在均不足以宣称交付。
- 只清理本任务创建、已证实完整集成且无未提交/未跟踪成果的 worktree 和本地分支。squash 集成需核对内容，不能因普通删除命令拒绝就强制删除；已推送的远端开发分支按项目清理规则或用户要求处理，不因本地合并就擅自删除。不清理用户或其他任务资源。
- 最终报告区分已实现、已验证、已集成、已推送、已部署/发布和阻塞状态，附对应证据；未通过必需验收时不关闭 issue、不声称完成。

## 阻断规则

遇到以下情况先自主调查或修复，确实无法解决时报告准确阻塞，只请求最少必要信息；可独立完成的工作继续推进：

- 缺少权限、凭据、设备或环境；操作超出已有授权，或涉及破坏性/不可恢复动作。
- 无法获取最新主线，无法安全推送开发分支、同步本地 `main`、集成任务结果，或无法满足完整主线发布门槛。
- 必需测试、review、发布任务或版本自动递增检查未通过。
- 缺少 PC/移动端发布到 Release 的任务，或任务副作用、目标环境、远端部分发布状态无法确认。
- 根因不明、只能样本特化，或用户意图与 issue、代码、运行事实明显冲突。

不要把等待、排队、跳过或缺少验证报告成成功；也不要对已有授权的常规步骤反复请求确认。

## 示例

- `gogogo 修复 #123`
- `gogogo https://github.com/org/repo/issues/45`
- `gogogo 修复这个导入错误，从建 issue 到上线全跑完`
- `gogogo 把这个需求直接做完并发版，不要每一步都停下来确认`
